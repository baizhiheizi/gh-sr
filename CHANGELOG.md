# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Release builds are tagged as `vMAJOR.MINOR.PATCH`. Each Git tag triggers a
[GitHub Release](https://github.com/an-lee/gh-sr/releases); the workflow also
generates release notes on publish. Use this changelog for a concise, curated
history when you want more than the auto-generated GitHub summary.

## [Unreleased]

### Added

- **`gh sr disk usage`: shared-volume rows.** Issue #559 proposal 4 (the measurable slice). The Linux host section of the disk-usage table now includes one `volume` row per `gh-sr-*` Docker volume — the `shared_caches` volumes (npm, `~/.cache`, gradle, pub, mise, android-sdk) plus any older gh-sr volumes — measured through one throwaway `busybox` container mounting every volume at once (volume data under `/var/lib/docker/volumes` is only readable via the daemon; the busybox pull itself rides the Docker Hub mirror). Watching these rows grow next to the existing `gh-sr-cache` / `gh-sr-registry` rows is the local proxy for how many WAN bytes the shared caches and mirrors are absorbing — no external router-side tracker needed. Best-effort by design: a Docker failure yields row-level errors rather than a failed report, and hosts without gh-sr volumes (or Docker) get no rows. The registry-mirror guide also documents how to verify the "fetched at most once per host" prefetch criterion from mirror storage growth and access logs.
- **Host-side content-addressed cache for `container_runner_image.toolcache` sources.** Issue #559 proposal 3. The toolcache bake is a single Docker `RUN` layer, so Docker cannot partially reuse it: any list edit (even one added tool), any base-image bump, and any builder-cache prune re-ran the **whole** loop and re-downloaded every tarball over the WAN — on a bake carrying the 1.6 GB Flutter tarball, that is hours of metered egress per rebuild. Before building, gh-sr now downloads each toolcache URL once into `~/.gh-sr/toolcache-src/<sha256(url)[:16]>` on the host (same retry/dead-socket/total-time curl policy as the bake; atomic `.tmp`+`mv` so a partial download can never be mistaken for a complete blob), links the blobs into the build context (`toolcache-blobs/`, hardlink with copy fallback), and the bake prefers them — falling back to its own WAN download only when the pre-sync failed, i.e. the pre-cache failure semantics. The image layout revision still fingerprints the config alone (the manifest's fifth column is context-only), so revisions stay deterministic per config across hosts with different cache states. First rebuild after upgrading downloads into the cache once; every later rebuild reads local disk. `rm -rf ~/.gh-sr/toolcache-src` reclaims the space. Also documents a "what survives `gh sr rebuild`" table in the rebuild command docs (registration, inner docker-data, shared volumes, prefetch reload vs. the container writable layer).
- **Multi-upstream registry mirrors + image prefetch (`gh sr images sync`).** Issue #559 proposal 2 (the GHCR half). dockerd's `registry-mirrors` is Docker-Hub-only **by construction** — moby's `loadMirrors` attaches mirrors solely to the `docker.io` index config, dockerd never reads containerd's `hosts.toml` (zero occurrences in the moby tree; upstream gap tracked as moby/moby#41456), and `/etc/docker/certs.d` carries CA certs only. So gh-sr cannot transparently redirect `ghcr.io` pulls; instead the new surface makes each non-Hub image cost **one WAN fetch per host instead of one per runner**: `registry_mirror.mirrors` (max 8) deploys one extra `registry:2` pull-through container per entry (`gh-sr-registry-<name>`, ports 5578+, optional `username`/`password_env` for private GHCR — the PAT is read from the environment, never stored in runners.yml), and `registry_mirror.prefetch` lists images that `gh sr images sync` — plus an automatic pass after `gh sr up` / `gh sr rebuild` — pulls once on the host and streams into every runner's inner dockerd (`docker save | docker exec docker load`), skipping runners that already have the exact image by ID. The host-side pull goes through the matching mirror on `127.0.0.1:<port>` (each mirror now also publishes on loopback — dockerd treats `127.0.0.0/8` as insecure, so the plain-HTTP mirror is pullable without touching the host daemon's config), so cached layers survive host image prunes and the mirror's access log doubles as the "fetched at most once per host" acceptance check. Backward compatible: `mirrors[0]` **is** the legacy Docker Hub mirror (container `gh-sr-registry`, wired into runner daemon.json as before) and inherits the legacy `port`/`upstream` keys; the first `mirrors:` deployment recreates the existing `gh-sr-registry` container once (deploy layout v2 adds per-mirror credentials and the loopback publish; mirrored layers are preserved). Tag references are restored with their tags; bare digest refs land their layers untagged — prefer tags. `gh sr doctor` reports per-mirror health and probes prefetch mirrors from a runner; `gh sr registry status` lists every mirror; `gh sr disk usage` sums their storage.
- **`shared_caches`: gradle / pub / mise / android_sdk volumes.** Four new sub-flags next to `npm` / `home_cache`, extending the per-host shared-cache story to the caches the traffic data blamed for rebuild cold-starts (issue #559 step 1): `gradle` mounts `gh-sr-gradle-cache` at `/home/runner/.gradle` (one `GRADLE_USER_HOME` per host — Gradle's cross-process file locks make a shared `GRADLE_USER_HOME` safe), `pub` mounts `gh-sr-pub-cache` at `/home/runner/.pub-cache` (`PUB_CACHE` default; pub writes each package version atomically), and `mise` mounts `gh-sr-mise-data` at `/home/runner/.local/share/mise` (`MISE_DATA_DIR` default — mise's CI guide endorses caching `installs/`, the download cache is already shared via `~/.cache`, and all containers run as the same uid 1001, sidestepping the known multi-user permission issues of shared mise dirs). All three mount at the tools' **own default cache locations**, so — unlike an env-var approach — nothing has to survive the entrypoint's `su -` login-shell reset. `android_sdk: true` (opt-in, default **off**) mounts `gh-sr-android-sdk` at `/opt/android-sdk` and exports `ANDROID_SDK_ROOT`/`ANDROID_HOME` to job steps via the runner `.env` (`GH_SR_ANDROID_SDK_ROOT` baked at container-create; the SDK has no default location, hence the env var). gradle/pub/mise default **on** like their siblings; doctor verifies containers carry the new mounts and flags ones that predate the config (`gh sr rebuild <name>`). The image bakes all mount points runner-owned, and the entrypoint re-asserts ownership on every start. Motivated by ~65 GB/day of metered WAN egress on a 12-runner host, of which Gradle/Maven (~8.4 GB/day), npm misses, and mise re-installs were the cacheable share; the volumes also cut cold-start spikes after `gh sr rebuild`.
- **`npm_registry`: npm registry override for container runners.** Top-level config string injected as `GH_SR_NPM_REGISTRY` at container-create; the entrypoint writes it into the runner user's `~/.npmrc`, which npm/npx/pnpm read under the runner user (a `docker -e` env var alone would not survive the entrypoint's `su -` login-shell reset). Intended for routing package installs through a regional mirror reachable without the WAN proxy (e.g. `https://registry.npmmirror.com` on China-network hosts, where it is kernel-routed around the clash core entirely instead of consuming proxy quota). Workflow-level `NPM_CONFIG_REGISTRY` env still wins by npm precedence. Opt-in and read its docs before enabling on a shared pool: bun ≥ 1.4 reads `~/.npmrc` too, mirrors can 404 on unpublished/unsynced versions, and repos with pull_request registry guards (canonical-registry-by-policy) fail on every PR run — the trial pool enabled it, hit all three, and settled on `shared_caches` only. Existing pools pick the wiring up with `gh sr rebuild <name>`; doctor warns about containers that predate the setting.
- **`shared_caches:` per-host shared cache volumes (default on).** Two named Docker volumes mounted into every container-mode runner: `gh-sr-npm-cache` at `/home/runner/.npm` (one npm cacache per host — content-addressed and safe for concurrent writers) and `gh-sr-runner-cache` at `/home/runner/.cache` (job-time download caches: pinned Chrome-for-Testing builds, pip, …). Cold caches are paid once per host instead of once per container and survive `gh sr rebuild` (volumes outlive container recreation; only `docker volume rm` drops them). The image bakes both mount points runner-owned, and the entrypoint re-asserts ownership on every start. The `.toolcache` is deliberately **not** shared — it is seeded by the `container_runner_image.toolcache` bake and a shared volume would freeze the first image's bake forever. Section fields: `enabled` / `npm` / `home_cache` (all default **true**); doctor checks that containers actually carry the mounts.
- `container_runner_image.toolcache`: pre-extract tool tarballs into the container runner image's tool cache at build time (`url` + `dir` + optional `complete` marker path, so `ruby/setup-ruby` & co. skip their runtime download). Both `tar.gz` and `tar.xz` archives are supported (xz covers e.g. Flutter stable, which ships tar.xz only), and an optional per-entry `strip:` (0–16, default 0) passes `--strip-components` at extraction so a top-level-wrapped archive (e.g. an Adoptium JDK `jdk-<v>+<b>/` tarball) extracts as the bare tool dir. Runtime tool installs keep working for anything not listed; the image tag/layout revision change with the list, so existing containers need `gh sr rebuild <name>`. Motivated by intermittent TLS resets on GitHub release-asset downloads leaving cold containers failing `Setup Ruby` unattended.
- **Docker registry pull-through mirror**: one `gh-sr-registry` container is deployed per Linux host (stock `registry:2` with `REGISTRY_PROXY_REMOTEURL`), and container runners' inner dockerd is wired to it via `daemon.json` `registry-mirrors` (`GH_SR_REGISTRY_MIRROR` env, baked at container-create) so every runner on the host shares one copy of each Docker Hub image layer instead of each re-downloading it over the WAN — the difference between N× and 1× bytes on metered uplinks. New `registry_mirror:` config section (`enabled` defaults to **true**; port, bind address, storage path, image, upstream, URL override), new `gh sr registry status|deploy|remove [--purge-data]` commands, a mirror row in `gh sr disk usage`, a dedicated guide (`guides/registry-mirror.md`), and doctor checks for mirror health, runner-side reachability (with the exact firewall allow rule), and containers that predate the mirror. Docker Hub only — dockerd has no per-registry mirror mechanism for ghcr.io; existing pools pick the wiring up with `gh sr rebuild <name>`.
- **Local Actions cache server**: one `gh-sr-cache` container is deployed per Linux host ([falcondev-oss/github-actions-cache-server](https://github.com/falcondev-oss/github-actions-cache-server)), so `actions/cache` reads and writes local disk instead of round-tripping GitHub. Runner containers receive `CUSTOM_ACTIONS_RESULTS_URL` pointing at the host's docker0 gateway; non-cache traffic (artifacts, safe-outputs) still passes through to GitHub. New `cache:` config section (`enabled` defaults to **true**; port, bind address, storage path, retention, size caps, image, management key, URL override), new `gh sr cache status|deploy|prune|remove [--purge-data]` commands, a cache row in `gh sr disk usage`, and doctor checks for cache health plus a **runner-side reachability probe**: a default-deny INPUT firewall (ufw et al) silently blackholes container→host-port traffic — every `upload-artifact` / `actions/cache` step times out while the host-side health check stays green — so doctor probes the URL from inside a runner container and FAILs with the exact allow rule when blocked. Deployments are stamped with a layout label and `Ensure` recreates containers deployed by older layouts. Only container-mode runners are wired; the server binds the docker0 gateway IP by default so it is reachable from runner containers but not from the LAN, and publishes on a fixed uncommon port (27420, override with `cache.port`) so hosts that already run a dev service on 3000 do not collide.
- `gh sr doctor --check-lockfiles`: scans each scoped repo's compiled gh-aw workflows (`*.lock.yml`, up to 20 per repo) for retired sudo/iptables-era artifacts (`sudo -E awf`, `docker-sudo-iptables`, a host-network `gh-aw-mcpg` gateway) and **FAILs** with a `gh aw compile` instruction; WARNs when `compiler_version` is below v0.88.0. Requires network access to the GitHub API.
- `container_runner_image.base_image`: override or digest-pin the fork runner base image used to build `gh-sr/agentic-runner` (default `ghcr.io/falcondev-oss/actions-runner:v2.337.0`). Changing it changes the image fingerprint, so existing containers need `gh sr rebuild <name>`.
- Organization-level self-hosted runners are now first-class: a dedicated [Organization runners](https://an-lee.github.io/gh-sr/guides/org-runners/) guide covers repo vs org scope, runner groups, workflow targeting, authentication, security, and migration from per-repo pools. The `org` / `group` fields in `runners[].yml` are documented in the config reference, an org-scoped runner example is added to `config/runners.yml` and `internal/config/runners.yml.template`, and a new "Organization runners" entry is registered in the guides index. `gh sr runner add --org` / `--group` and the existing `org:` / `group:` config fields are the public entry points; `gh sr doctor` reports `org <name>: list runners OK (<n> registered)` and prints an `admin:org` / org-owner hint on 403. `gh sr status` and the TUI now show a uniform `target=org:<name> [group=<name>]` (or `target=owner/repo` for repo-scoped runners) via a new `RunnerConfig.DisplayTarget()` helper. (#187)
- Added `BenchmarkLoad_Small`, `BenchmarkLoad_Large`, `BenchmarkValidate_Small`, and `BenchmarkValidate_Large` benchmarks in `internal/config` to establish a performance baseline for config loading and validation. Run with `make bench`. (#37)

### Changed

- **Breaking — agentic runner image layout v2 (rootless sandbox)**: the locally built `gh-sr/agentic-runner` image now derives from a fork runner base (`ghcr.io/falcondev-oss/actions-runner`) and runs the gh-aw v0.88+ sandbox **rootless** — no `sudo`, no iptables rules; the AWF firewall runs unprivileged on the inner Docker bridge and inner containers resolve `host.docker.internal` via `--add-host=host.docker.internal:host-gateway`. Compiled workflows built before gh-aw v0.88 **no longer run** — recompile with `gh aw compile` (`gh sr doctor --check-lockfiles` flags the retired artifacts). The image fingerprint changed, so run `gh sr rebuild <name>`; `gh sr doctor` reports stale images.
- `gh sr down` on container-mode runners is faster for multi-instance configs: `docker stop` and `docker rm -f` now run in a single SSH round-trip per instance instead of two, reducing round-trips from 4N to 3N (~25% fewer SSH calls for an N-instance teardown). (#264)
- `gh sr doctor` now runs host SSH checks and GitHub API checks (repos and orgs) concurrently, reducing wall-clock time from O(N × latency) to O(latency) for configurations with multiple hosts or targets. Output within each section is printed in sorted order. (#33)
- `gh sr service install`, `gh sr service uninstall`, and `gh sr service status` now open one SSH connection per host concurrently via `runPerHostParallel`, matching the behavior already in place for `up`, `down`, `restart`, `update`, and `status`. For single-host configs there is no observable difference; for multi-host configs completion time drops from O(N × SSH_latency) to O(SSH_latency). Output order across hosts is non-deterministic. (#30)

### Fixed

- **`gh sr disk usage` no longer reports every shared volume as "empty or missing" when the measurement itself fails.** The shared-volume measurement runs `docker run … busybox du -sb /v/* | sed …`, so the pipeline's exit status is `sed`'s: if `docker run` fails — most plausibly because `busybox` cannot be pulled on an offline or metered host that has no pull-through mirror configured — the command still exits 0 and every volume was attributed the "volume empty or missing" fallback. That misdescribes real cache directories *and* silently omits their bytes from the host total on the exact command whose job is to warn about disk pressure. A total failure is now detected (no parseable output at all) and reported as such on every row, while a genuinely absent directory still falls back to the per-volume message.
- **The container runner image no longer ships a second copy of every tool-cache tarball.** The host-side source cache (#559 proposal 3) hands `docker build` a `toolcache-blobs/` directory of pre-downloaded archives, and the bake `COPY`-ed it into the image. `COPY` writes into a persisted layer, and deleting the files in a later layer cannot reclaim layer bytes — so every rebuilt image carried a full duplicate of the sources next to the extracted tool cache (the Flutter entry alone is ~1.6 GB), on exactly the hosts where runner disk is tightest. The bake now runs in a throwaway `toolcache-bake` stage that inherits the same base layers (no duplicated apt/curl work), and the final image carries over only the extracted `/home/runner/.toolcache`. The image fingerprint changes; run `gh sr rebuild <name>`.
- **The tool-cache source cache lands in `~/.gh-sr/toolcache-src`, not a directory literally named `$HOME`.** The generated pre-download script single-quoted its cache paths (`'$HOME/.gh-sr/toolcache-src/<key>'`), and single quotes suppress parameter expansion — so the shell created a directory called `$HOME` relative to the SSH session's working directory and cached there. The cache would still have worked, but nothing else in gh-sr knows that path: it is inconsistent with every other host state dir, invisible to `gh sr disk usage`, and silently stops hitting if the working directory ever differs between builds. Cache paths are now double-quoted so the remote shell expands `$HOME`.
- **`gh sr disk usage` measures every configured registry mirror instead of reporting 0.** The multi-mirror storage measurement single-quoted the *joined* list of mirror directories (`du -sb -c '<base> <base>-<name>'`), so `du` received one argument containing a space, measured nothing, and — because its stderr was suppressed and the empty grand total still parses — reported **0 bytes** for every host with two or more `registry_mirror.mirrors` entries (exactly the documented Docker Hub + ghcr setup). Each directory is now quoted separately and every output line is matched back to its own path, so a mirror whose directory does not exist yet reports 0 without shifting its siblings' sizes. The row-per-mirror rewrite also fixes the attribution: disk usage now emits one row per mirror (container name against **its own** storage dir) instead of one `gh-sr-registry` row carrying the combined total of every mirror under the first mirror's path. `$HOME` is resolved once per listing instead of once per mirror.
- **`gh sr images sync` no longer reports a host-side "already on host" count that was always 0.** The counter was documented as "image already in the host store", but `syncPullOnHost` returned `pulled=true` on every success, so every run printed `N pulled (0 already on host)`. `docker pull` must contact the registry to learn whether a `:latest` moved, so there is no meaningful already-present case to count on the host — the counter and the phrase are gone. The per-runner `cached` skip (matched by image ID) is the one that saves real work and is unchanged.
- **Registry mirrors dropped from `runners.yml` are surfaced by `gh sr doctor`.** `Ensure` and `gh sr registry remove --purge-data` only iterate the *configured* mirror list, so renaming or deleting a `mirrors:` entry left its container running (`--restart unless-stopped`) with its storage directory still occupying disk, reachable by no `gh sr` command and reported by neither `gh sr disk usage` nor `gh sr registry status`. Doctor now reconciles on-host `gh-sr-registry*` containers against the configured list and WARNs per orphan with the `docker rm -f` command to run. Best-effort: an unreadable container list stays silent rather than turning into a failure.
- **`runners.yml.template` is valid YAML again.** Two stray `+` lines (leftover patch artifacts) sat before the `registry_mirror` and `npm_registry` comment blocks, and as bare top-level scalars they made the whole template unparseable — a fresh config copied from the template failed `Load` with `expected '<document start>', but found '<scalar>'` before a user had touched anything. Removed.
- **Image `apt-get` now resolves through a CN mirror (`APT_MIRROR` build arg, default TUNA).** The fork base ships stock Ubuntu archive sources, so every `apt-get update`/`install` went to `archive.ubuntu.com` / `security.ubuntu.com`. Measured from a cn-region runner host that link sustained only **60–338 KB/s** against **6–11 MB/s** from the CN mirrors the toolcache bake already uses — so the several-hundred-MB `clang`/`cmake`/`gtk-3-dev`/`gstreamer-*` manifests dominated build wall time, not the 1.6 GB Flutter bake. The rewrite is a targeted in-place `sed` over `/etc/apt/sources.list` and `/etc/apt/sources.list.d/*.{list,sources}` (deb822, which is what noble uses), catching both archive endpoints over http and https, rather than overwriting a sources file — that matters because the base also carries the git-core PPA (`ppa.launchpadcontent.net`), which has no CN mirror and would be lost by a wholesale replace. Override with `--build-arg APT_MIRROR=...`, or pass an empty value to keep the upstream archives. The image fingerprint changes; run `gh sr rebuild <name>`.
- **Image downloads no longer hang forever on a stalled transfer.** Every `curl` in the agentic runner image carried `--retry 8 --retry-all-errors` but only `--connect-timeout`, which bounds TCP connect and nothing else. A connection that came up and then stalled without a FIN/RST — the documented `release-assets.githubusercontent.com` TLS-reset case, which the Dockerfile already names as the one GitHub host that fails from cn-region/x1 hosts — left curl blocked in `read()` indefinitely: `--retry` never saw an error, so the build neither failed nor progressed. Observed on a pool rebuild stuck 25 minutes on the first 49 MB bake entry with one second of CPU. All five curls now also pass `--speed-limit 10240 --speed-time 60` (dead socket becomes a fast retryable abort) and a per-payload `--max-time` (300s small files, 600s the compose binary, 1800s the toolcache bake), so a live-but-pathological link fails loudly instead of wedging — measured at ~42 KB/s, which alone put the 1.6 GB Flutter entry ~10 h out. `--retry-all-errors` keeps both timeouts retryable rather than fatal on the first attempt.
- **`container_runner_image.toolcache` bake no longer strands intermediate tool-cache dirs root-owned.** The bake ran as root and chowned only each entry's leaf dir, so the parents `mkdir -p` created stayed root-owned — `Ruby/<ver>` left `Ruby/` behind, `node/<ver>/x64` left both `node/` and `node/<ver>/`. A workflow pinning a version the bake doesn't carry then hard-failed instead of installing it at job time: on a pool baking Ruby 4.0.7, `baizhiheizi/ohmyxin`'s `.ruby-version` 4.0.5 made `ruby/setup-ruby` die with `EACCES: permission denied, mkdir '/opt/hostedtoolcache/Ruby/4.0.5'` (every agentic job on that pool, from the container-generation change that picked up the new image). The bake now chowns the whole tool-cache root once after the loop, so a bake miss degrades to a normal runtime install — the behavior the "Runtime install fallback preserved" scenario already required. Same latent break guarded for future node patch bumps. Run `gh sr rebuild <name>` to adopt; the image fingerprint changes with it.
- The agentic runner image now bundles the **Docker Compose CLI plugin** (sha256-verified, `container_runner_image` build arg `COMPOSE_VERSION`). gh-aw's rootless sandbox starts its squid proxy and agent containers via `docker compose`, but the fork base's static Docker bundle ships buildx without compose — agent jobs died at "Execute Claude Code CLI" with `unknown shorthand flag: 'd' in -d` (exit 125). Run `gh sr rebuild <name>` to adopt the fix.
- Container-mode runners now pin their Docker MTU to the host's egress MTU, fixing workflow downloads (e.g. `actions/setup-go`, `actions/setup-node`) that failed with `Client network socket disconnected before secure TLS connection was established` on hosts whose real path MTU is below 1500 (cloud overlay networks such as GCP's 1460 default, VPN/WireGuard, nested virtualisation). The outer container's `eth0` and the inner `dockerd` bridge previously kept Docker's 1500 default; with PMTUD black-holed, large TLS-handshake packets were silently dropped while small packets (and the host itself) worked. `gh sr` auto-detects the host egress MTU at container-create time and `entrypoint.sh` applies it to both layers (plus an MSS clamp for forwarded inner traffic). Run `gh sr rebuild <name>` to adopt the fix. A `container_runner_image.mtu` override is available for hosts where a tunnel lowers the path MTU below the NIC MTU, and `gh sr doctor` flags a stale image as `container-mtu`.
- The agentic runner image now bundles **Node.js LTS** (NodeSource) and `npm` on `PATH` for `gh-aw` activation setup. `gh-aw` v0.79+ enables `safe-output-artifact-client` during activation, which runs `npm install` *before* `actions/setup-node`; a stale image with no `npm` aborted with `npm is not available. Cannot install @actions/artifact package.` Run `gh sr rebuild <name>` to pick up the fix. `gh sr doctor` flags a stale image as `container-node-npm` (see the [Agentic Workflows guide](https://an-lee.github.io/gh-sr/guides/agentic-workflows/) → §6 Health checks / §8 Troubleshooting).

### Removed

- Retired agentic-image hacks made obsolete by the rootless sandbox: the Docker CLI shim (gateway `--hostname`/`--name` rewriting), the baked `daemon.json` + dnsmasq DNS (inner containers now get `host.docker.internal` from `--add-host=host.docker.internal:host-gateway`), the AWF service-routing iptables bypass, and the passwordless sudoers entries. gh-aw and AWF are no longer preinstalled in the image — jobs install their own tooling, so the image builds faster and stays smaller.
